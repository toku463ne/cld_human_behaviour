### 余剰があって売れない理由を、もう1つ潰した

**最初の読みでは「掲げているものの選び方」が疑わしかった**——**身体は手の先頭を掲げ、60%が飾り物を持っている**ので、**皮が counter に載ることがほとんど無い**可能性があった。**`HandOverCheapest`（段階84）を足した腕で確かめた**:

| | `coatbite` | `coatbitespare` | `coathiderich` | `coathidespare` |
|---|---:|---:|---:|---:|
| `sales` | 2.33 | 0.92 | 1.42 | 1.92 |
| `hidesSold` | — | — | **0.00** | **0.00** |
| `hidesGiven` | — | — | 130 | 128 |
| `hidesSpare` | — | — | 0.89 | 0.60 |

**12シード全部で 0.00。** **一番惜しくないものを掲げさせても、余った皮は128回人手に渡り、そのうち売買は0回。**

### 結論——段階68 以来の診断が、ここで外れた

**「足りないのは買い手ではなく売り手」**（段階68）**は、7つの段階の前提だった**。**今回、売り手はいた**: **余りを持ち**（`hidesSpare` 0.89）、**掲げてもいて**（`HandOverCheapest`）、**それを手放しもした**（128回）。**ただし1回も売らなかった。**

**動かないのは、手渡しが無料で即時だから。** **贈与は好意を買い、代価がゼロで、相手が硬貨を持っている必要もない。** **売買は、硬貨を持った買い手が歩いてくるのを待つ。** **同じものを手放すのに、片方は今すぐ確実に得があり、もう片方は条件が揃うのを待つ**——**余剰があるかどうかは、この比較を1ミリも変えない。**

**そして「贈与に値段を付ける」は4度測って4度とも交換そのものを消している**（段階84d・段階88・`coatpriced`・#115(a)）。

**したがって、防寒具を商品にする案はここで閉じる**（`TODO.md` の8番が先に決めてあったとおり、87a・88・`coatrare`・`coatpriced` に続く5度目）。**規則は残す**（`HidePerBudget` / `WardNeedsHide`。**既定はオフ**）——**材料そのものは世界を悪くしない範囲で動いており、地図の作者が「獣を狩らないと冬を越せない土地」を作るのに使える。**

**次に市場を狙うなら、触る場所は品物ではなく手渡しの側**（#115(a)）。**ただしそれは4度潰れているので、同じ形では入れないこと。**

### 作りながら見つけたもの

- **1本の手と材料は排他になる**（`canCraft` が「作った物を置く場所」を訊くので、**唯一の手に皮を持っている身体は、その皮を加工できない**）。**材料は加工と同時に手を出るので、そこは「作れる」とした**——**手の枠のある世界でだけ現れる deadlock で、枠の無い世界では見えない**
- **`selfView` は決定ごとに作られる**ので、**皮の2つの図は規則がオンのときだけ計算する**（`BenchmarkDecide` 21.0 → 21.4µs ＝雑音の中。**素直に毎回計算すると +3%**）
- **指紋テストは無変更で通った**——**既定の世界に皮は1枚も落ちないので、乱数列が1つも動かない**


## 2026-09-20 指1本で遊べるようにした（`TODO.md` の9番）——そして「フレーム数で測る」を2度間違えた

**タップで狙い、同じところをもう一度タップで既定の行動、長押し（0.5秒）でメニュー。** **`engine` は1行も変えていない**（入力の層だけ。命令は今までどおり `OrderHuman` を通る）。**キーもマウスも残る。**

### 作ったもの（`cmd/devview/touch.go`）

- **指とマウスを1つの層に入れた**（`pointer`）。**2つの入力経路が食い違わないため**で、**副作用として、クリックは「押した瞬間」から「離した瞬間」に変わった**（それがタップの定義）
- **既定の行動は4つ**: 食料＝食べる／外敵＝攻撃／人＝観察／地面＝そこまで歩く。**人を2タップで殴らない**——取り消せないことを2タップにしない（攻撃は長押しのメニュー）
- **長押しのメニュー**は、その狙いに意味のある命令だけを並べる。**数字キーでも選べ、外をタップすれば閉じる**
- **メニューを質問にも使った**。**後継選び・求愛の返事・訊かれるモードの質問・節目の選択**は「短い一覧から1つ選ぶ」で同じ形なので、**どこをタップしてもその選択肢が出る**。**数字キーだけだった4つが指で答えられるようになり、新しい訊き方は1つも足していない**

### フレーム数で測って、2度間違えた

**最初の実装は「30フレーム押されたら長押し」だった。** **2つの理由で間違い**:

1. **遅い端末では長押しが1.5秒になる**（20fps なら）。**ジェスチャは人の手の動作なので、人の時計で測る**
2. **ブラウザで実測したら、1秒に4フレームしか来なかった**（後述）。**押している間に1フレームも来ない**ので、**タップすら成立しない**

**直したあと**: **時間で測り**（`holdDelay` 500ms）、**押している間に1フレームも来なかった長押しは、指を離した時点で長押しとして扱う**。**指が 8px 超ずれたらどちらでもない。**

### ブラウザで実際に確認した（WASM ＋ 合成タッチイベント）

**`GOOS=js GOARCH=wasm` でビルドし、WSL から配信して Windows の Chrome（headless）で開き、ページの JavaScript から `TouchEvent` を canvas に投げた**（ebiten は `targetTouches` を読むので、これは電話が送るものと同じ）。**`go.argv` をページから渡せる**ので、`-play` で最初から手綱を握った状態にできる。

**結果**: **タップで狙いが付き、同じところをもう一度タップで `walking to the ground at 164,560 - it stops when it gets there`、長押しで4項目のメニュー**（`walk here` / `rest` / `effort 1.0 -> 0.2` / `think again`）**が描かれた**。**手綱を握っていないときの長押しも確認**（`node:` / `stop the clock`）。

**手順で2つ躓いた。どちらも次に同じことをする人が踏む**:

- **`--virtual-time-budget` を使うとフレームが来ない**。**40秒ぶんの仮想時間で描かれたのは4〜6フレーム**（＝1秒に1〜4フレーム）。**仮想時間は wall clock を圧縮するが rAF は実フレームなので、合成した押下が1フレームも見られずに終わる**。**外したら 3.6秒で136フレーム（約38fps）になった**
- **仮想時間を外すと Chrome の `--screenshot` が使えない**（読み込み直後に撮ってしまう）。**代わりにページ自身に撮らせた**——**`requestAnimationFrame` の中で `canvas.toDataURL()` を呼び、ローカルのサーバに POST する**。**ebiten は `preserveDrawingBuffer` を付けていないので、フレームの外で読むと空になる**

**この手順は `cmd/devview` を電話で確かめる唯一の道**なので、`PLAN.md` の「ブラウザで遊ぶクライアント」に書いた。

### 残っているキーボード専用

**エディタ（F3）・速度（`-` / `=`）・ズーム（`z`）・パネルの切り替え（Tab）・履歴（`[` / `]`）・後継の指名（`k`）・構え（`s`）・保存（F2）。** **遊ぶのに要るのは構えとズームくらい**で、**それは 10番（描画をタイルに）で画面の作りを変えるときに一緒に決める。**


## 2026-09-20 円をやめて絵で描いた（`TODO.md` の10番）——絵のほうが速かった

**身体と物は、1枚のシートから貼る 16px の絵になった**（`cmd/tiles` が焼き、`cmd/devview/tiles.go` が貼る）。**`-circles` で以前の描き方に戻せる。**

### 実装前に数えた（遊ぶ地図 `-terrain country`）

| | |
|---|---:|
| 1画面に描くもの | **260**（人・獣・物・倉庫） |
| そのうち画面の中 | **260**（全景では全部。**何も間引いていなかった**） |
| ネイティブ（WSLg のソフトウェアGL） | 25 fps |
| ブラウザ（wasm / Chrome headless） | **13.9 fps** |

**「1画面300枚」という見積もりは当たっていた**（260）。**そして数えて初めて分かったことが1つ**——**画面の外のものも全部描いていた**。**遊ぶズーム（2.5倍）では、270 のうち画面にあるのは 52**。

### 決めたこと

- **1枚のシート**。**同じテクスチャからの描画は何枚貼っても1バッチ**なので、260枚が問題にならない
- **灰色で描いて、貼るときに色を付ける**（`ColorScale`）。**色は「誰の身体か」「何の物か」を言う**ので、色を焼き込むと**身体60体×物8種類ぶんの絵**が要る
- **絵は `cmd/tiles/art.go` に1文字1ピクセルで書く**（`.` 透明・`o` 輪郭・`b` 本体・`s` 陰・`e` 目）。**この project に絵描きはいないが、文字で地図を描く習慣はある**——地形・地域・天気・植物・外敵の置き場は全部その形（決定#133）
- **ファイル名に中身のハッシュ、manifest を読んでから開始**。**ネイティブは埋め込み、ブラウザは `fetch`**——**15MB の wasm と 1.4kB の絵は変わる頻度が違う**
- **円が持っていた読みは全部残す**。**輪の太さ＝攻撃力、輪の色＝状態、尾＝速さ、帯＝空腹**、**「円の塗り＝残り体力」だけは絵にできないので緑の帯にした**

### 測定（同じ wasm を `-circles` と対で。遊ぶ地図・6秒ずつ）

| | 円 | 絵 |
|---|---:|---:|
| ブラウザ（Chrome headless、wasm） | **11.0 fps**（86/7531・86/8111） | **14.4 fps**（118/7280・105/7502・99/7576） |
| ネイティブ（WSLg・llvmpipe） | 10 fps | 11 fps |

**予想と逆だった。** **絵にすると重くなると思っていた**（貼る枚数が増えるので）**が、ブラウザでは3割ほど速くなった**。**理由は ebiten の `vector` が Go 側で三角形に分解すること**——**円1つがコマンドではなく頂点の計算**で、**wasm ではそれが効く**。**ネイティブの差は雑音の中**（このマシンの GL はソフトウェアで、同じ設定で 25 fps と 10 fps が出る）。

**あわせて画面の外を間引いた**（`onCamera`）。**遊ぶズームで 270 のうち 52**＝**5分の1**しか描かない。**HUD に `drawing 52 of 270 things  18 fps` を出した**ので、これは以後いつでも読める。

### 見た目の確認

**ネイティブと、WASM をブラウザで**（`TODO.md` の9番で作った合成タッチの手順をそのまま使った）。**遊ぶズームで、人は立ち姿・獣は四つ足、川には魚、地面には草とコイン**。**タップと長押しも絵の上でそのまま動く**（長押しのメニューが出た）。

**手順で1つ引っかかった**: **ebiten は画像を読み込むときに自分用の小さな canvas を作る**ので、**ページの最初の canvas はゲームの canvas ではない**。**合成タッチを投げる相手は「一番大きい canvas」で選ぶ。**

## 2026-09-20 好みが動く（段階90）——出来事の数え上げを10倍外し、売買は速さでしか動かなかった

**`TODO.md` の12番の2つ目。** **継いだ好み（`taste`）は素質のまま残し、そこから「今の気に入り」を引いて持たせる**（`TrinketFancyTicks` / `TrinketFancySpread`。**既定はオフ**）。**遺伝も予算も1ミリも動かない。**

### 実装前に数えて、外した
