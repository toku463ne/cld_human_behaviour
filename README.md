# cld_human_behaviour — 操作方法

人間の振る舞い・適応・相対的能力・資源・進化をテーマにした、ゲーム要素のあるシミュレーション（1人 = 1ノード）。

**この文書には「今の操作方法」だけを書きます。** 変わったら上書きし、古い記述は残しません。

| 知りたいこと | 見る文書 |
| --- | --- |
| どう動かすか | この文書 |
| いつ何が変わったか・なぜそう決めたか（設計判断ログ） | `HISTORY.md` |
| 今どうなっているか（アーキテクチャ・規約・原則・ロードマップ） | `CLAUDE.md` |
| これから何を作るか（実装計画のチェックリスト） | `PLAN.md` |
| ノードが従うルール | `NODE.md` |
| 外敵が従うルール（未実装） | `ENEMY.md` |
| パラメータの一覧と既定値 | `PARAMETERS.md` |

## 必要なもの

- Go 1.24 以上（`go.mod` は 1.24.0。動作確認は go1.24.0 linux/amd64）
- `cmd/devview` の描画に ebiten を使うので、GUIが出せる環境（WSL2 + WSLg、`DISPLAY=:0` で動作確認済み）
- 外部依存は ebiten のみ。`go run` すれば取得される

## ビルドと検証

```bash
go build ./...
go vet ./...
go test -race ./...
```

この3つが常に通ることがコーディング規約です。ホットパス（`engine` のtickループ、近傍探索、大量ノードを走査する処理）に触れたときは、変更の前後でベンチマークを取ります。

```bash
go test ./engine/... -run=^$ -bench=. -benchmem
```

`-run=^$` で通常のテストを飛ばしてベンチだけ回します。`BenchmarkEngineStep`（300体）／`BenchmarkEngineStepCrowded`（混雑時）／`BenchmarkDecide`（効用比較1回）の3本。

特定のテストだけ動かす例:

```bash
go test ./engine/ -run TestCorneredAgentRunsFromTheOneKillingIt -v
```

## シミュレーションを見る（cmd/devview）

`protocol` / `server` / `client` はまだ無いので、現状の唯一の実行方法は開発用ビューアです。`engine` を直接importしてその場に描画します（ネットワークなし）。

```bash
go run ./cmd/devview                  # そのまま眺める
go run ./cmd/devview -follow 7 -slow  # ノード#7を1/5速度で追う
```

| オプション | 意味 |
| --- | --- |
| `-follow <ID>` | 起動時からそのノードを選択（追跡）する。0で選択なし |
| `-slow` | 1/5速度で開始する |
| `-seed <n>` | 乱数シード（既定1）。同じシードなら常に同じ結果になる |

### 操作

| キー / 操作 | 動作 |
| --- | --- |
| クリック | ノードを選択して追跡（右パネルにそのノードの意思決定が出る） |
| Esc | 選択解除 |
| スペース | 一時停止 / 再開 |
| → または `n` | 1tickだけ進める（自動的に一時停止する） |
| `-` / `=` | 速度を落とす / 上げる（1/10・1/5・1/2・通常・高速） |
| `[` / `]` | 意思決定の履歴を1つ前 / 後に送る（直近16件） |
| Tab | 右パネルを「意思決定トレース」と「他者への強さ推定」で切り替える |

### 画面の読み方

- 円の大きさ＝体力、輪の太さ＝パワー、下のバー＝空腹度、塗り色＝性別（青＝男性／桃＝女性）
- 輪の色＝状態: 灰＝採食／橙＝求愛／緑＝ペア／赤＝戦闘／紫＝逃走／青＝休息
- 赤い線＝殴っている相手、灰色の線＝ペア
- 選択中のノードには黒い輪が付き、そのノードが今狙っている対象（食料・相手）にも輪が付く

### 右パネル（意思決定トレース）

選択中のノードが `Decide()` を呼んだときの記録です。

- **asked because** — 何がきっかけで考え直したか（spawned / target lost / goal reached / attacked / vitality drop / idle / food in sight / bond ended / controller set）
- **at the time** — そのときの体力・空腹度・競合度
- **compared N options** — 比較した全候補をスコア順に表示。`=>` が選ばれた手
  - 1行目: 行動と最終スコア（`misjudged` は頭の良さによる評価のブレ。低いほど大きく、これが原因で最善手を外すことがある）
  - 2行目: 目的の内訳 `目的 価値x確率=寄与`（life 生存 / stake 争っている食料 / rival 将来の競合の排除 / offspring 子孫 / info 相手を知る / explore 探索）
  - 3行目: コスト `cost vit 体力=-減点  time tick数=-減点`、および `risk`（その相手に過去払わされた体力）

意思決定はトリガー方式なので毎tick起きません。何も表示されないときは、そのノードにまだ再判断の理由が来ていないだけです。

### 1ノードを追うときの手順

1. `-slow` で起動するか、`-` を数回押して速度を落とす
2. 追いたいノードをクリック（`-follow` で最初から指定してもよい）
3. スペースで止め、`→` で1tickずつ進める
4. 行動が切り替わった瞬間に右パネルを読む。`[` で1つ前の決定に戻れる

追跡は指定したノードだけ記録されます（全ノードを常時記録すると重いため）。

## ルール変更をA/Bで測る（cmd/experiment）

devview は「世界が破綻していないか」は見えますが、「このルール変更で知能への選択圧が +3 になったのか −2 になったのか」は目で見えません。それを測るヘッドレスのランナーです。

```bash
go run ./cmd/experiment -list                                   # 用意されている条件を見る
go run ./cmd/experiment -variants baseline,nogate               # 既定 12シード x 20000tick
go run ./cmd/experiment -variants baseline,nogate,gate20 -seeds 24 -ticks 60000
go run ./cmd/experiment -variants baseline,nogate -csv out.csv  # 推移をCSVに出す
```

| オプション | 意味 |
| --- | --- |
| `-variants a,b,c` | 比較する条件（`-list` で一覧）。既定 `baseline,nogate` |
| `-base <name>` | 差分の基準にする条件。既定は `-variants` の先頭 |
| `-seeds <n>` | 条件あたりのシード数（既定12） |
| `-seed0 <n>` | 最初のシード（既定1）。全条件が同じシード列を使う |
| `-ticks <n>` | 1回あたりのtick数（既定20000） |
| `-interval <n>` | サンプリング間隔（既定200tick） |
| `-csv <path>` | 推移の時系列をCSVで書き出す |
| `-jobs <n>` | 並列実行数（既定CPU数） |

出力は2つの表です。

- **per arm** — 条件ごとの平均 ± 標準誤差
- **paired difference** — 基準条件との差を**同じシードどうしで引き算**した平均 ± 標準誤差。シード間のばらつきは条件差よりずっと大きいので、対にして引かないと何も見えません。`*` は差が標準誤差の何倍か（`*`=1倍、`**`=2倍、`***`=3倍）の目安で、検定ではありません

読み方の例: `dIntelligence +4.52 +/-0.95 ***` は「その条件にすると、20000tickで平均知能の上がり幅が 4.52 大きくなる。標準誤差0.95なので向きは信用してよい」。

主な指標:

| 指標 | 意味 |
| --- | --- |
| `dPower` / `dRationality` / `dIntelligence` | 平均能力が開始時からどれだけ動いたか＝**その能力への選択圧**。能力値は最後の1tickではなく末尾2割の平均で読む |
| `killShare` | 死因に占める「殺された」の割合。食料供給を振ってもほとんど動かないので、争いの多さを見るのに使いやすい |
| `clumping` | 同じ個体数を一様にばらまいた場合と比べて、どれだけ集まっているか。**相対値**で、1が一様という意味ではない（視界の円が世界の端で切れるぶん低めに出る）。条件間で比べる |
| `neighbours` / `nearest` | 平均的な個体の視界内にいる他個体数／最近傍までの距離 |
| `clusters` / `clusterSize` | 集団の数（2体以上の連結成分）と、その平均サイズ。連結の距離は 30（`engine.DefaultClusterLinkDist`）で固定。**距離が違う測定値どうしは比べられません** |
| `gap` / `gapP10` | **集団間の距離分布** — 各集団から最も近い別の集団までの距離（メンバー間の最短距離）の平均と下位1割。**連結距離30より短い値は原理的に出ません**（30以内なら同じ集団になるので）。`gapP10` が30に張り付いているなら、近い集団どうしは接触寸前 |
| `gapRel` | 上の平均を、同じ数の集団を無作為にばらまいた場合の期待値で割ったもの。**1が「構造なし」**（実測で0.98。`TestClusterGapsRelativeOfARandomLayout`）。1未満＝偶然より寄り集まっている、1超＝互いを避けている |
| `halfLife` | **membership half-life** — 同じクラスタにいた2体の組のうち半分が離れるまでのtick数。「集団」と「たまたま近くにいる塊」を区別する唯一の指標。片方が死んだ組は**離れたとは数えません**（在籍時間ではなく寿命を測ってしまうため） |
| `together` / `censored` | 500tick後もまだ一緒にいる組の割合／半減が窓（2000tick）の中で起きなかった実行の割合。`censored` が0でないなら `halfLife` は窓の端に張り付いた**下限値**なので、`together` のほうを比べます |
| `fightCompanion` / `fightStranger` | 遭遇100回あたりの戦闘数（%）。**遭遇＝`CombatRadius` 以内にいる組**で、`fightCompanion` は200tick前から同じクラスタにいた組、`fightStranger` はそうでない組 |
| `fightRatio` | 上の比（仲間 ÷ よそ者）。**1を下回るほど「集団の中では戦闘が少ない」。** 素直な「集団内戦闘率 ÷ 集団間戦闘率」が測れない理由は下記 |
| `species` | 最後の観測時点で生き残っている種族の数。**今は必ず1**（human だけ）。0なら絶滅 |
| `rareShare` / `rareTrough` / `rareSwing` | **種族ごとの個体数** — 一番少ない種族（今は human＝全体）の、直近5000tickの窓での「全体に占める割合」「窓の最小値 ÷ 平均（＝**振動の谷がどこまで下がるか**）」「(最大−最小) ÷ 平均（＝振動の大きさ）」。読むのは `rareTrough` のほうです。あるべき状態Aは**振動そのものは許す**ので、振れ幅の大きさは単独では何も言わず、**谷が0にどれだけ近づいたか**だけが「その種族が消えるか」を決めます。1に近いほど平ら、0なら絶滅 |
| `grouped` / `largestShare` | 2体以上の集団に属する個体の割合／最大の集団に属する割合。`largestShare` は他の3つの信頼性チェックで、1に近いなら世界が1つの塊につながっただけ（単連結は数珠つなぎになる）で、集団数は何も意味しません |
| `starved` / `killed` / `aged` | 死因の内訳。合計が `deaths`。`aged` は寿命消費（過小・過度な食事が背景で寿命を削る、`CLAUDE.md` 参照）が0まで達したケースで、既定値ではほぼ発生しない（`brittlelifespan` 条件で確認できる） |
| `extinct` | 絶滅した回数の割合。0でないなら他の数字は読む価値がない |

`fightRatio` の注意: **「集団間の戦闘」は書かれたとおりには測れません。** 打撃が届くのは `CombatRadius`（15）以内だけで、これはクラスタの連結距離（30）より短いので、殴り合っている2体は**その瞬間つねに同じクラスタにいます**（実測で20000tick中、クラスタ内5994・クラスタ間0）。そこで「同じ遭遇を、**200tick前から一緒にいた組（仲間）か、そうでない組（よそ者）か**で分ける」形にしてあります。どちらも遭遇あたりの率なので、仲間のほうが近くにいる回数が多いことだけで答えが決まることはありません。

新しい条件を試すときは `cmd/experiment/main.go` の `variants` に1項目足します（`engine` 側に分岐を作らず、`Config` を書き換える関数として書く）。両方の条件が同じバイナリに入っていないと、同じシードで対にして比べられません。

## 集団のようすを画像で残す（cmd/snapshot）

数値（`clusters` や `halfLife`）は「集団がいくつあるか」「半減期が何tickか」を言いますが、**その集団がどんな形をしているか**や**曲線がどんな形か**は言いません。`cmd/snapshot` は記録用の画像をPNGに描き出す、ヘッドレスの開発用ツールです。

```bash
# 世界の1瞬間（クラスタごとに色分け）
go run ./cmd/snapshot -seed 1 -ticks 50000 -out docs/images/clusters-<commit>.png

# membership の生存曲線（複数シードの平均）
go run ./cmd/snapshot -mode curve -seeds 8 -out docs/images/membership-<commit>.png
```

| オプション | 既定値 | 意味 |
| --- | --- | --- |
| `-mode` | `world` | `world`＝世界の1瞬間、`curve`＝membership の生存曲線 |
| `-seed` | 1 | 実行のシード（`world`） |
| `-seeds` | 8 | 平均するシード数（`curve`。1〜この数を使う） |
| `-ticks` | 50000 | 描く前に進めるtick数 |
| `-link` | 30 | クラスタの連結距離（`engine.DefaultClusterLinkDist`） |
| `-scale` | 2 | 世界の1単位あたりの出力ピクセル数（`world`） |
| `-commit` | （空） | 画像に焼き込むコミット。省略すると現在のHEADを `git` から読む（作業ツリーが汚れていれば `-dirty` が付く） |
| `-out` | `snapshot.png` | 出力先 |

`-mode world` の画像の読み方:

- **同じクラスタの個体は同じ色**で、その間に細い線が引かれます。**色は使い回されるので、離れた別のクラスタが同じ色になることがあります** — 何が1つの集団かを決めているのは線であって色ではありません
- **灰色の点は singleton**（連結距離の中に誰もいない個体）。1体は集団ではないので色を与えていません
- 薄い緑の点は食料
- 下の帯に seed / tick / 連結距離 / 個体数 / クラスタ数 / 平均サイズ / 集団に属する割合 / 最大成分の割合 / **コミット** が入ります。画像がリポジトリの外に出ても、どの条件のどのコミットのものか分かるようにするためです

`-mode curve` の画像の読み方:

- 横軸は**ラグ（tick、対数）**、縦軸は「その時点でまだ同じクラスタにいる組の割合」。半減期が60tick付近なのに末尾が2000tickまで伸びるので、対数軸でないと片方が潰れます
- **薄い線が各シード、濃い線がその平均。** 平均だけを見て「どの実行でもこうなる」と読まないため
- 赤い破線が平均の半減期。**片方が死んだ組は「離れた」と数えていません**（在籍時間ではなく寿命を測ってしまうため）
- 曲線が対数軸で直線にならない＝**単一の指数関数ではない**ことがこの絵の要点です。速い成分（すれ違い）と遅い成分が混ざっています

どちらのモードも、同じオプションなら常に同じ画像になります（`engine` が決定的なので）。`-link` を振ると、連結距離という「目盛り」を変えたときに見え方がどう変わるかを比べられます（値の決め方は `HISTORY.md` の 2026-08-31 の項）。
